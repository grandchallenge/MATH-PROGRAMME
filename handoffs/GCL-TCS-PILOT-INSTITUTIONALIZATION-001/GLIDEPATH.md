# GLIDEPATH — first executable tranches and agent operating contract

## Agent staffing rule

One execution lead owns the transaction. Additional agents are specialists, not a standing approval committee.

Spawn specialist agents only when parallel investigation, domain expertise, adversarial analysis, or genuine separation of duties is materially useful. Their findings are evidence inputs. They do not create extra gates.

A Referee is invoked only when the governing transition materially requires independent review. A Human Steward is invoked only when the governing instrument materially reserves the decision. Do not simulate a Council or approval committee for routine bounded work.

## Mandatory first-output contract

Before mutation, the execution lead must produce a compact preflight containing:

```text
LIVE PROTECTED HEAD
LIVE ESTATE MEMBERSHIP
CONTROLLING DOCTRINE REVISIONS
GHOS MATERIAL-STATE RESULT
MATH-CORE CAPABILITY STATE
GCL-TCS v1.0 READINESS MATRIX
EXISTING REUSABLE TOOLING
PROPOSED FIRST TRANCHE
MATERIAL CLOSURE
AFFECTED CHECKS
AUTHORITY REQUIRED: delegated / reserved
CHECKPOINT REQUIRED: yes / no
```

If `AUTHORITY REQUIRED` is `reserved`, cite the exact protected rule and exact material transition. “This is important” or “the template contains G8/G9” is not evidence of a reserved gate.

If `CHECKPOINT REQUIRED` is `yes`, cite the live checkpoint-admission doctrine and show why this operation qualifies as an explicitly admitted multi-session governed campaign. Do not create checkpoint paperwork otherwise.

## Recommended first-tranche ordering

### Tranche 0 — live reconciliation and readiness baseline

- Re-fetch protected sources listed in `README.md`.
- Reconcile the live installed `grandchallenge` estate against historical GHOS material state.
- Re-read live rulesets/protection relevant to any proposed implementation.
- Re-fetch current GCL-TCS v1.0 acceptance criteria and build the readiness matrix.
- Map existing evidence, including GHOS, to acceptance rows without assuming satisfaction.
- Inspect existing tooling/validators/workflows before proposing new machinery.
- Decide checkpoint eligibility explicitly.

Output: a bounded gap/readiness record and the smallest safe implementation tranche.

### Tranche 1 — shallow discovery surface

Correct the known evidence-discoverability weakness with the smallest non-authoritative index/pointer surface. Do not edit terminal GHOS ledger/campaign/closure/source objects merely for navigation. Route only affected cheap/proportional checks.

### Tranche 2 — detect-only GHOS material sentinel

Implement the narrowest detector that compares live material identities against governed dependencies and emits classification/revalidation routes. It is read-only/detect-only by default. Derive any workflow topology from actual bytes and route it under GHOS. Do not grant mutation authority merely because detection is automated.

### Tranche 3 — heterogeneous pilots

Use real artifacts. Cover all six current required classes or record explicit deficits. For mathematical work apply `MATH_CORE_INTEGRITY.md` and the domain-authority firewall. Do not manufacture migrations or publications only to satisfy a row.

### Tranche 4 — measurement and successor evaluation

Aggregate defects, false positives/negatives, burden, ambiguities, exceptions, recurring failures, discoverability/orphan/stale-reference results, prevented invalid transitions and unnecessary friction. Produce an honest readiness/evaluation package. Do not assume v1.0 promotion is the correct outcome.

The ordering is advisory. Reorder if live protected state demonstrates a smaller or safer dependency path.

## Routine integration sequence

For each bounded tranche:

1. classify material closure;
2. run only affected checks;
3. recover/repair through the authorized recovery ladder if needed;
4. exercise standing delegated disposition;
5. protected merge with exact-head guard where available;
6. protected-main readback;
7. update durable successor records only when their own material state changed.

Do not run an approval cycle after readback.

## Anti-pattern card

Do not:

- treat this handoff, illustration, issue body or agent summary as authority;
- reopen terminal GHOS because later estate/material state changes;
- turn every new repository into a full historical-estate replay;
- put GHOS, MATH-CORE and GCL-TCS into one giant state machine;
- make MATH-CORE a universal artifact registry;
- make GCL-TCS a second mathematical Claim Ledger or MATH-CORE blackboard;
- infer canonical acceptance from a certificate, graph edge, MATH-CORE event or transport identity;
- add Human Steward/Referee approval because a generic template has those roles;
- rerun expensive CI for unrelated material closures;
- grant a persistent/write-capable sentinel when a read-only detector suffices;
- create a checkpoint unless live doctrine admits it;
- create new tooling before inspecting existing implementations;
- make AETHER a correctness dependency;
- publish a P06 pilot externally merely to demonstrate public-profile conformance;
- promote a pilot conclusion beyond the underlying domain evidence.

## Positive operating heuristics

- Prefer immutable identity and dependency maps over timestamps.
- Prefer pointers to canonical records over copied summaries.
- Prefer impact-routed cheap attestations over expensive unaffected replays.
- Prefer one transaction owner plus specialists over standing committees.
- Preserve failed attempts when they reveal control quality or burden.
- Distinguish readiness from authority.
- Distinguish working mathematical state from accepted/canonical state.
- When two procedures protect the same material boundary equally well, use fewer gates, reruns, actors and persistent components.

## Stop discipline

A genuine stop must name the exact boundary and object. Examples: reserved authority, materially changed dependency, unavailable authentication after fallbacks, security/protected-state boundary, C04-C07 capability transition, insufficient substantive evidence, or exhausted recovery routes.

Ordinary CI pending, unrelated `main` movement, a repairable bug, a connector limitation with an authorized fallback, another session, or a documentation change is not by itself a stopping boundary.
