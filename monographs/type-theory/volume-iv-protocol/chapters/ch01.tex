
\chapter{A Program With Someone on the Other End}

A closed function is patient. It can wait until all of its inputs are available, reduce internally,
and eventually return a value. A conversation cannot be described that way without losing the
order in which information becomes available.

Consider a client and a service. The client first sends a natural number. The service then replies
with a Boolean. The interaction is not merely associated with the payload types
\(\Nat\) and \(\Bool\). It also contains an order:
\[
   \text{send }\Nat \quad\text{then}\quad \text{receive }\Bool \quad\text{then close}.
\]

\begin{principle}
For an interactive computation, ``what may happen next'' is part of the type-level obligation.
A protocol type is therefore not only a description of data. It is a description of admissible
continuations.
\end{principle}

\section{From values to traces}

Suppose an ordinary function has type
\[
  f : \Nat \to \Bool.
\]
The type says that a natural-number input is mapped to a Boolean result. It does not say that
another independently executing party must be ready at an intermediate point.

Now consider the finite interaction
\[
  C \xrightarrow{\,42\,} S
  \qquad
  C \xleftarrow{\,\mathsf{true}\,} S.
\]
The arrows are events. After the first event, both peers are in a new protocol state. The next
permitted action is different from the action permitted before the first event.

\begin{warningbox}
A trace is not a function value written sideways. A protocol can remain open indefinitely, can
branch on messages from another party, and can depend on scheduling. Closed evaluation and open
interaction have different semantic burdens.
\end{warningbox}

\section{The smallest session language}

For the first executable kernel, payload values are drawn from a small ordinary value language.
Session types are generated by
\[
  S ::= \send{A}{S} \mid \recv{A}{S} \mid \mathsf{end!} \mid \mathsf{end?}.
\]
The intended reading is directional from the endpoint whose type is being written.

\begin{definition}[Output session]
\(\send{A}{S}\) requires the endpoint to send one value of payload type \(A\), then continue
according to \(S\).
\end{definition}

\begin{definition}[Input session]
\(\recv{A}{S}\) requires the endpoint to receive one value of payload type \(A\), then continue
according to \(S\).
\end{definition}

\begin{definition}[Closing endpoints]
\(\mathsf{end!}\) requires active close; \(\mathsf{end?}\) requires the peer-facing wait for close.
They are kept distinct so that endpoint obligations remain complementary.
\end{definition}

The client protocol above is therefore
\[
  S_C = \send{\Nat}{\recv{\Bool}{\mathsf{end!}}}.
\]
The protocol is an ordered object. Swapping the first two constructors changes the protocol.

\input{plates/plate02}

\begin{intuition}
Read a session type from left to right as a program counter for communication. Each constructor
says which action is legal at the current frontier and which type governs the continuation after
that action is discharged.
\end{intuition}

\section{Processes}

The full Volume-IV preflight defines a richer process language. In this chapter we need only
output, input, close, wait, and inaction:
\[
 P ::= 0
 \mid x!\chanval{v}.P
 \mid x?(y).P
 \mid \mathsf{close}\;x.P
 \mid \mathsf{wait}\;x.P.
\]

The process
\[
  x!\chanval{42}.x?(b).\mathsf{close}\;x.0
\]
has exactly the visible protocol shape of \(S_C\), assuming \(42:\Nat\) and \(b:\Bool\).

\begin{formal}
A process typing judgment has the form
\[
   \ptypes{\Gamma}{\Delta}{P}.
\]
The value context \(\Gamma\) contains ordinary reusable assumptions such as \(b:\Bool\).
The channel environment \(\Delta\) contains endpoint obligations such as
\(x:\send{\Nat}{\recv{\Bool}{\mathsf{end!}}}\).

At Gate 1 we use this judgment only for local derivations. Parallel composition and environment
splitting are introduced in Chapter 2.
\end{formal}

A schematic output rule is
\[
\frac{
  \Gamma\vdash v:A
  \qquad
  \ptypes{\Gamma}{\Delta,x:S}{P}
}{
  \ptypes{\Gamma}{\Delta,x:\send{A}{S}}{x!\chanval{v}.P}
}.
\]
The premise for the continuation uses \(x:S\), not the original output type. Communication
therefore consumes an obligation.

Likewise, a schematic input rule is
\[
\frac{
  \ptypes{\Gamma,y:A}{\Delta,x:S}{P}
}{
  \ptypes{\Gamma}{\Delta,x:\recv{A}{S}}{x?(y).P}
}.
\]

\section{Worked trace}

\begin{workedexample}
Take
\[
 S_C=\send{\Nat}{\recv{\Bool}{\mathsf{end!}}}.
\]
The event sequence
\[
  \mathsf{send}:\Nat,\quad
  \mathsf{recv}:\Bool,\quad
  \mathsf{close}
\]
consumes the constructors of \(S_C\) in order and reaches the terminal state.

By contrast,
\[
  \mathsf{recv}:\Bool,\quad
  \mathsf{send}:\Nat,\quad
  \mathsf{close}
\]
uses exactly the same two payload types but violates the protocol at the first step.
\end{workedexample}

This is the first lesson that session types add beyond an ordinary product or function type:
\emph{ordering is type-relevant}.

\section{Computational laboratory}

\begin{labbox}
Run
\[
  \texttt{python labs/lab01_protocol_trace.py}.
\]
The laboratory parses finite protocol descriptions, checks traces action-by-action, and runs
positive and hostile fixtures. It deliberately rejects wrong order, wrong payload type,
premature termination, and trailing events.
\end{labbox}

The implementation uses a deterministic trace validator because reproducible evidence is useful.
The mathematical protocol language is not thereby defined to have only one scheduler.

\section{Do not confuse: the protocol with the meaning}

Imagine a payment service whose protocol requires
\[
  \mathsf{send}:\Nat;\ \mathsf{recv}:\Bool.
\]
A client may send \(0\) where the business rule requires a positive amount. The communication can
be protocol-correct while the application is wrong.

\begin{warningbox}
Session fidelity constrains communication shape. It does not by itself establish business
invariants, security properties, persistence, fault tolerance, or the semantic truth of payloads.
Those are separate proof obligations.
\end{warningbox}

\section{Exercises}

\subsection*{Checkpoint}
\begin{enumerate}[label=\textbf{1.\arabic*}]
\item Translate ``send a natural number, receive a Boolean, then close'' into the Gate-1 session notation.
\item Explain why \(\send{\Nat}{\recv{\Bool}{\mathsf{end!}}}\) and
\(\recv{\Bool}{\send{\Nat}{\mathsf{end!}}}\) are different protocol types.
\item State the role of \(\Gamma\) and the role of \(\Delta\) in
\(\ptypes{\Gamma}{\Delta}{P}\).
\end{enumerate}

\subsection*{Core}
\begin{enumerate}[label=\textbf{1.\arabic*},start=4]
\item Write a process skeleton that follows
\(\send{\Bool}{\send{\Nat}{\mathsf{end!}}}\).
\item Give a valid action trace for
\(\recv{\Nat}{\recv{\Bool}{\mathsf{end?}}}\).
\item Give two distinct invalid traces for
\(\send{\Nat}{\recv{\Bool}{\mathsf{end!}}}\), one with the wrong order and one with the wrong payload type.
\end{enumerate}

\subsection*{Synthesis}
\begin{enumerate}[label=\textbf{1.\arabic*},start=7]
\item Compare the information contained in a function type \(\Nat\to\Bool\) with the session type
\(\send{\Nat}{\recv{\Bool}{\mathsf{end!}}}\). Name one fact each type expresses that the other does not.
\item Explain why a deterministic trace checker can be valid evidence for finite examples without
turning the mathematical process semantics into a deterministic semantics.
\end{enumerate}

\subsection*{Proof Workshop}
\begin{enumerate}[label=\textbf{1.\arabic*},start=9]
\item Prove by inspection of the four constructors that every finite Gate-1 session type has a
well-defined first communication action.
\item Give an induction principle for finite Gate-1 session types and use it to prove that the
number of actions in a complete trace equals the number of session constructors consumed.
\end{enumerate}

\subsection*{Design Clinic}
\begin{enumerate}[label=\textbf{1.\arabic*},start=11]
\item Extend the trace syntax with a payload-value predicate, such as ``positive natural'', without
claiming that ordinary session fidelity already enforces it. State what new checking layer you added.
\end{enumerate}

\subsection*{Challenge}
\begin{enumerate}[label=\textbf{1.\arabic*},start=12]
\item A service is intentionally nonterminating: it repeatedly receives a request and sends a reply.
Explain why ``does not normalize to a final value'' is not by itself a correctness defect. State
which additional formal machinery is needed before this example belongs to the Volume-IV calculus.
\end{enumerate}
