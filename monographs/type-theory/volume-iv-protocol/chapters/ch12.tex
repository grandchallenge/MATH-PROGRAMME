\chapter{Watching the Conversation}

Static typing judges source structure before execution. A runtime monitor observes events after execution has begun. The two techniques can share a session description, but they have different information and different failure modes.

\section{Compile a finite session to an automaton}
For each finite local session type, construct a monitor state for each residual type. A send constructor expects an observed send event with the declared payload class; a receive constructor expects the complementary local event; selection and branching inspect labels; terminal states inspect close/wait. A transition advances to the continuation state.

\section{Observed-trace soundness}
\begin{theorem}[T4.20, monitor soundness for observed finite traces]
If the \texttt{PROTO-MON1} monitor generated from finite session type $S$ accepts a complete, fully observed local trace $\tau$, then $\tau$ is a valid complete local trace of $S$ under the monitor's event abstraction.
\end{theorem}
\begin{proof}
By induction on $S$. Every generated monitor state has transitions only for the event class licensed by the outer session constructor. Acceptance advances to the monitor generated from the continuation. Branch constructors dispatch only to registered labels. Terminal constructors accept only their corresponding terminal event. Thus an accepted complete trace follows the session structure constructor by constructor.
\end{proof}

\section{What the monitor cannot see}
An application may send a natural number with the wrong business meaning. A transport may duplicate a frame below the instrumentation boundary and later de-duplicate it. A peer may crash before an event is emitted. The monitor can reason only about its observed event stream and any trusted metadata attached to those events.

\section{Static and dynamic evidence}
Static typing can rule out some bad programs before they run, but only relative to the source/compilation model. Monitoring can detect violations caused by untyped components or deployment drift, but only after observable events occur. Neither technique universally subsumes the other.

\section{Do not confuse: monitor rejection with diagnosis}
\begin{warningbox}
A monitor can report that the observed trace violated its automaton. It does not automatically explain the root cause, repair the protocol, or establish completeness for unobserved distributed failures. T4.21 remains an explicit non-result.
\end{warningbox}
