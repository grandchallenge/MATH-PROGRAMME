## Purpose

GH-OS provides durable execution routing for bounded, replaceable conversational agents: workflow-byte classification, persistent-controller admission, candidate-independent enforcement, hostile rejection, and protected readback.

This campaign extends those guarantees across active `grandchallenge` repositories or records an explicit governed non-applicability disposition. It does not redesign GH-OS and does not create mathematical, certification, constitutional, publication, production, or commercial authority.

## Campaign invariant

For every active repository, a fresh operator must be able to answer from durable protected state:

1. What direct execution surfaces exist?
2. What safety-relevant features are present in their actual bytes?
3. What execution topology is required?
4. Which controller, if any, is admitted to provide that topology?
5. Which candidate-independent required check enforces the routing decision?
6. Which material evidence proves the protected repository is conformant?

No registry entry, README, issue statement, candidate-local validator, or agent assertion may downgrade a topology derived from executable workflow state.

## Per-repository procedure

For each unresolved repository:

1. bind repository identity, default branch, relevant protected head/dependencies, current rulesets, and workflow inventory;
2. determine whether routing is applicable;
3. derive execution features from direct workflow bytes;
4. derive the minimum topology rather than copying another repository's declarations;
5. bind an admitted controller to each non-bounded workflow, or decompose it into independently recoverable bounded transactions;
6. add the repository-local registry, deterministic validation evidence, and protected-base enforcement using the shared pinned gate where compatible;
7. require `routing-enforcement` in protected policy with the repository's intended **non-strict** concurrency semantics unless a materially different policy is explicitly justified;
8. run affected repository policy/security/conformance checks selected by current policy;
9. execute repository-specific hostile proof where the authority risk warrants it;
10. obtain specialist review only for the material security/constitutional/provenance/certification boundary that requires it; routine implementation uses standing delegation;
11. merge through protected controls and read back protected main, enforcement bytes, registry, ruleset, controller identity, and required checks;
12. record one terminal repository disposition in the estate ledger.

Do not require a synchronization commit solely because protected `main` advanced. Do not launch unrelated full-estate or mathematical replay solely to make evidence numerically fresh.

## Phase-1 implementation note

The MATH-PROGRAMME reference enforcement workflow cannot be copied byte-for-byte into every repository because dependency surfaces differ. Preserve the candidate-independent execution model and pinned shared gate while adapting installation steps to the target repository.

Do not silently change an existing repository's required-status strictness from non-strict to strict as part of routing rollout. Routing enforcement should add the required control without reintroducing update-branch serialization unless a separate policy decision justifies that material change.

## Hostile proof

A hostile candidate should attempt enough of the following to prove that the mandatory routing decision is outside candidate control:

- remove or bypass candidate-local routing validation;
- add an unregistered scheduled or write-capable workflow;
- declare a weaker topology than workflow bytes imply;
- bind an incompatible or absent controller;
- repin a reusable policy caller to a pre-enforcement revision;
- modify the enforcement workflow itself;
- alter shared-gate path or digest without the governed upgrade route;
- attempt to reuse evidence after materially changing the routing/security object.

Success means candidate-controlled checks may still pass while independently required routing enforcement fails and protected integration remains blocked.

## Persistent-controller admission

A controller satisfying `PERSISTENT_CONTROLLER_REQUIRED` needs evidence for durable wake, durable state, exact controller/repository identity, supported features, recoverable transactions where applicable, stale-evidence rejection, replacement recovery, interruption recovery, unauthorized-transition refusal, and separation of capability from authority.

The demonstrated repository-bound GitHub Actions controller may be reused only where the shared gate and local policy explicitly admit it for the repository and required features.

## Campaign-level controls

The campaign is multi-session and resumable. A conversational agent may execute bounded transactions but is not the sole persistent controller. Every repository tracker and campaign transition must leave enough durable state for replacement without chat reconstruction.

Avoid broad polling. Bind asynchronous observations to the material repository/run/job being observed. A pending external job is an external wait, not a reason for a conversational executor to remain alive.
